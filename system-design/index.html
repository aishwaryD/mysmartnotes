Introduction to system design

Understand how an application behaves as requests move through it—and what happens when part of that path slows down or fails.

A customer clicks "Export". The request reaches your application, a job is created, a worker reads the data, and a file becomes available. Then the worker crashes before acknowledging the job. Should the next worker create another file, reuse the first one, or start again?

System design gives you a way to reason about questions like this. The aim is to define what the user can expect, follow the work and durable state, and choose components that support that promise.

Define the requirement

"Make it scalable" is too vague to investigate. "Return a job ID within two seconds and make duplicate requests safe" gives you something to design and test. State your workload assumptions and failure behaviour before choosing infrastructure.

What you’ll learn

Start with requests, latency and load balancing. Then examine indexes, replication and partitioning before moving to queues, retries and observability. The sections connect what the user sees with the data and failure boundaries underneath.

Before you begin

Basic HTTP, SQL and application-development experience. You do not need a cloud account or a running cluster to work through the design exercises.

You can read everything for free. Worked examples, practice questions and relevant interactive exercises are included in the chapter where you need them.

How to practise

Take a feature you know and follow one request from the browser to its response. Mark where data becomes durable. At each remote call, ask what the caller knows if it times out. Keep the answers beside your design.

Try each exercise before opening its explanation. If an update surprises you, trace a smaller example. The goal is to make the reasoning your own.
